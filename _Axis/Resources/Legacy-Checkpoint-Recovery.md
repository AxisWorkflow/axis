# Legacy Checkpoint Recovery
> **Purpose:** Recover a known old-checker refusal without losing dirty project work or bypassing normal Git checks.

Load only when the installed checker blocks an update checkpoint on cross-transaction evidence pairing, an explicit parent supervision reference or a timestamp-shaped scratch path. Other refusals follow ordinary Link Maintenance. This is a narrowly reviewed maintenance repair before resuming the existing updater, not permission to execute downloaded tools.

1. **Establish scope.** The affected project's live Main owns the repair. Require its exact-root Git repository, exclusive local writer and existing authority for this compatibility repair. A parent may provide a proposal but never writes the child's Git state or borrows its session. Retain the original diagnostic, installed version/checker hash, HEAD, staged diff and working diff. Preserve every untracked file and split staged/unstaged edit. Do not stash, reset, rewrite records, add blanket exceptions or bypass hooks.
2. **Match exact bytes.** Read `legacy-checkpoint-patches.json` as data. Select only an entry whose `before_sha256` matches the ordinary, single-link installed `_Axis/Resources/record-check.py`. Refuse unknown/customized bytes, links, a staged checker change, a checker differing from HEAD, an unfinished update transaction or any other writer. A verified release or trusted parent can supply a proposed data file where the old installation lacks it; review it under the child's existing maintenance authority, never as new authority. Do not run a downloaded helper or load target boot instructions.
3. **Prepare and review.** In isolated scratch, apply each literal `before` → `after` replacement exactly once to the preserved installed text. Refuse any missing/duplicate match or an output hash different from `after_sha256`. Review the entire diff: only transaction-local rename pairing and, where present, masking exact parent supervision references and scratch path spans are covered. Parent references remain externally unverified; the child must retain the delegation evidence separately. Adjacent local identifiers, Markdown destinations, immutable-record changes and normal filename checks still apply. A different repair needs its own bounded review.
4. **Preserve before installing.** Write one durable maintenance Log with the diagnostic, authority, original and proposed hashes, reviewed diff, recovery-copy location and normal checks to run. Save the complete checker preimage and mode with a create-only recovery receipt outside disposable scratch. Do not place this maintenance receipt under `_Axis/Updates/` or manufacture an updater transaction. Immediately recheck the lease, HEAD, index and all captured project bytes. Under an owned file lock, atomically replace only the checker, retain its mode and read back its exact hash. Do not change the index or any other existing file. Loss of ownership or unknown drift stops without speculative restoration.
5. **Check and resume.** Run the installed checker's existing `names`, `write-once` and, if supported, `links --staged`, plus the repository's ordinary Secrets, content and hook checks. Genuine defects still stop the checkpoint; keep all dirty work. Add the exact checker repair and maintenance receipt to the intended checkpoint only after reviewing the staged scope. Require a real normal commit, retaining any unstaged edits. Continue the updater's supported bootstrap and verify its later checkpoints. Do not claim adoption from the repair commit alone.
6. **Recovery.** Before the repair checkpoint, restore only this checker if its current bytes still equal the recorded patched hash, the original lease/lock is yours and HEAD/index are unchanged; read back the saved original bytes/mode. Otherwise preserve the receipt and stop for reviewed recovery. After a commit, use ordinary history-preserving Git recovery. Retain the failure and receipt even if the patch is rolled back.

The data covers only the exact official old checkers it names. It is never imported or scanned at startup or on ordinary turns. Missing data, unavailable exclusive storage or uncertain provenance leaves this recovery lane held; unrelated project work remains available.
