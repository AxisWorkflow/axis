# Settings
> **Purpose:** Record Application Settings and Mindset Settings for the Axis Workflow.

## Application Settings

### Project Time Zone

**Description:** The IANA timezone used to interpret and display User-supplied local Reminder times. `Unknown` requires an explicit UTC offset or UTC instant; the current host timezone is never silently adopted as project state.

**Range:** `Unknown`, `UTC`, or a valid IANA timezone such as `Europe/Zurich`.

**Value:** Unknown

### Storage Policy

**Description:** The persistent write-safety ceiling for this project. `auto` permits Axis to use a freshly verified `atomic` storage profile; `single-writer` always forces serialized one-writer behavior even when a local probe passes. This Setting can make writing safer but can never force or claim atomic storage.

**Range:** `auto` or `single-writer`

**Value:** auto

### Remote Freshness

**Description:** `on` authorizes one bounded Git fetch/check against the current branch's already configured upstream during each normal Main startup. Incoming or diverged commits produce a `^resume` recommendation; nothing merges or pushes automatically. `auto` does the same check and, when the upstream is simply ahead and the local checkout is clean (or holds only this session's lifecycle Logs), fast-forwards before the session reads the project, so it opens up to date; anything else is only reported (including commits this computer has not pushed yet), and nothing is ever merged, rebased, stashed or pushed. `off` makes no startup network request. New projects ship with `auto` (User decision, 2026-10-04); a project without a remote makes no request. Existing projects keep their stored value, and a missing Setting still means `off`. Git, Python 3, POSIX timeout support and verified local atomic storage are optional prerequisites for this enhancement; failure leaves Axis usable with freshness unverified.

**Range:** `off`, `on` or `auto`

**Value:** auto

### Auto Send

**Description:** With a configured Git remote, `on` commits and sends the project at each milestone (each Log Event the Main Agent writes, and `^shutdown`), so a computer left without `^save` has already sent its work. Sending follows the same rules as `^save`: only to the shared branch, never forcing, merging over conflicts or discarding. Anything else waits for the next `^save` or `^resume`. `off` sends only on `^save` and `^git`. A missing Setting means `off`.

**Range:** `off` or `on`

**Value:** on

### CX Frequency

**Description:** Cross-Examination is an effective way to stress-test key assumptions, logic, and output generated by an Agent. Performing more cross-examination, however, slows down the project and is computationally expensive. The purpose of this setting is to define when a Main Agent should spawn a CX Subagent to perform a cross-examination.

**Range:** 0 to 3, where:
> 0 = Never cross-examine
> 1 = Cross-examine only final decisions and deliverables
> 2 = Cross-examine key intermediate decisions, steps, deliverables, and problems
> 3 = Cross-examine every non-trivial decision, step, deliverable, and problem

**Value:** 1

### CX Model

**Description:** Main Agent can spawn a CX Subagent to stress-test key assumptions, logic, and output generated during a project. This setting names the LLM to use for the CX Subagent. The default `same-as-host` means: use the host's own model in an isolated context. A local model (e.g., installed via `^install ollama`, which overwrites this value) is cheaper and faster; a frontier model produces sharper critique. If this setting is not set or is broken, then halt and ask User to run `^install`.

**Range:** `same-as-host`, or any valid model name (local or remote) accessible to the host.

**Value:** same-as-host

### Local Model

**Description:** Many actions can be performed by a local LLM model that is more cost-effective. User, however, must install such models on their local machine for such models to work. Local models run via `ollama` - the sole supported local runtime. This setting names which LLM to use when running it locally. The tested starting default is Qwen3-VL 4B Instruct Q4 (`qwen3-vl:4b-instruct-q4_K_M`), the benchmark-recommended choice on the tested reference machines for eligible clerical work. On machines with more capacity, `qwen3:8b` is a scored but slower alternate whose extraction route remains conditional. Every choice still requires the per-machine `^install` aptitude check, and only matching task classes may be delegated. Treat reasoning-tuned models (`deepseek-r1:*`, `*-reasoning`) as benchmark-first - they historically overthink simple transforms, so delegate to one only on matching class-score evidence. Changing this value warrants re-running `^install` to re-test aptitude (the fixtures there set delegation expectations). If this setting is not set or is broken, and you are attempting to start a local model, then halt and ask User to run `^install` to install a local model.

**Range:** any valid **local** model name on current machine and accessible to Main Agent.

**Value:** qwen3-vl:4b-instruct-q4_K_M

### Working Language

**Description:** Querying, Searching, etc. work better in the same embedding space. The purpose of this setting is to direct LLM to harmonize all content into one language.

**Range:** Any language understood by the LLM.

**Value:** English

### Max Notes

**Description:** The number of active Notes kept in `_Axis/Notes/` (set a lower threshold for greater efficiency). When there are more, the oldest move unchanged to the Archive; Notes are never deleted.

**Range:** 0 to 100,000

**Value:** 250

### Model Access

**Description:** Choose subscription sign-in or an explicitly authorized API key at launch. Either prefers verified subscription access; it never grants paid fallback. Optional Model Access Claude and Model Access Codex sections use the same values. Credentials stay in the host secret store or private provider files in Secrets; workers never read them.

**Range:** subscription, api-key, either

**Value:** subscription

### Archiving

**Description:** How readily inactive history moves into tracked family-local Archive folders and external cold storage. Never suppresses history moves, including overflow/self-archiving, but does not retain completed recovery or regenerable scratch output. See [Practices > Archiving] for ages and holds.

**Range:** Never, Default, Aggressive

**Value:** Default

### Cold Storage Location

**Description:** Logical name of an approved external cold destination. Host paths bind locally in Flags; an unavailable device holds cold copying, not local archiving. Cloud sync alone is not verified remote upload.

**Range:** unconfigured or a logical name containing letters, digits, underscore or hyphen

**Value:** unconfigured

### Archive Location

**Description:** Legacy history lookup and migration location. Preserve this binding until existing archived records have verified mappings. New local archives use fixed tracked family-local Archive folders; this legacy value does not redirect new writes. Missing external history remains unavailable, never empty.

**Range:** `_Axis/Archive/` or an existing absolute, home-relative or project-relative folder path.

**Value:** _Axis/Archive/

### Archive in Git

**Description:** Legacy payload preference, preserved during migration. An existing false value never silently stages old ignored history. New family-local archives are tracked; cold payload remains external regardless of this legacy value.

**Range:** `true` or `false`

**Value:** true

### Tracking

**Description:** Activity tracking writes append-only lines to `_Axis/Tracking/{Session ID}.md` - the live channel where each Agent says what it intends, is doing, asks and finished, which every Agent, `^board`, `^audit` and the Dashboard read (see [Practices > Tracking]). Levels: `off` = never write; `commands` = session start, INTENT and DONE for each Command that changes something and each Subagent spawn and return, plus every ASK and REPLY; `writes` = `commands` plus INTENT and DONE for each unit of work that writes a shared file, with STATUS at milestones; `verbose` = `writes` plus step-level STATUS inside long protocols. Standard-capability Subagents track at `writes` and above; Local delegations never track (Main writes their INTENT and DONE lines instead).

**Range:** `off`, `commands`, `writes`, `verbose`

**Value:** writes

### Permissions

**Description:** How often Agents stop to confirm a change before making it (see [Rules > Permissions]). `Restricted` = confirm every change that deletes, overwrites or cannot be undone exactly; `Default` = act on clear intent when the change carries little risk (reversible, additive or verifiably disposable), and confirm unclear intent, new design or direction choices, live model work and irreversible loss; `Autonomous` = act on clear intent and confirm only when intent is unclear or a mistake could not be rolled back and would be major. No level removes `^pub`, `^update`, pushing, paid spending, Secrets, WORM (apart from exact reference repairs under [Practices > LinkMaintenance] and bounded repairs under [Practices > FaultTolerance]) or role gates, and every level reports what changed.

**Range:** `Restricted`, `Default`, `Autonomous`

**Value:** Default

### Fault Tolerance

**Description:** Bounded response to demonstrated minor non-compliance; load [Practices > FaultTolerance] when a check, deadline, expectation, milestone, budget or deliverable is missed. `-2` = strict compliance; `-1` = repair ordinary reversible defects before continuing; `0` = may disclose and tolerate a harmless cosmetic defect without editing its record, but no deadline grace; `1` = also permits bounded completion grace of up to 1% of the original duration (at most two minutes); `2` = also permits up to 5% completion grace (at most fifteen minutes) and audited, meaning-preserving WORM whitespace repairs. Grace applies only where the existing authority permits it; never raise a money cap, cross a hard deadline, weaken evidence or exceed role/host authority. Default is `1`; missing means `1`, malformed means `-2` until corrected. This is an Application Setting, not a Mindset adjustment or permission to lower acceptance criteria.

**Range:** `-2`, `-1`, `0`, `1` or `2`

**Value:** 1

### Max Concurrent Sessions

**Description:** The most Agent sessions that may be live on this project at once - Main, External Agents and Subagents together (see [Rules > MarkersFlagsAndLocks > Concurrent Sessions]). A new External Agent or Subagent does not start while the limit is reached; Main is never refused. Missing or malformed values mean `10`.

**Range:** a whole number from `1` to `100`

**Value:** 10

### Parent Authority

**Description:** How far this project's direct parent Axis Project may direct it (see [Practices > Subprojects > Parent Authority]). `direct` = an order User gives in the parent with `^^do` binds this project and outranks its standing instructions for that task: its own session carries it out after a checkpoint, refers it back to you, or declines it for a stated reason. `advise` = parent orders are ordinary requests this project may decline. Use `advise` when someone other than the parent's User runs this project. Only you, working in this project, can raise it to `direct`. Missing means `direct`; a malformed value means `advise`. A project with no parent ignores it.

**Range:** `direct` or `advise`

**Value:** direct

### Context Management

**Description:** How the Agent decides what project records to read for each request (see [Practices > Context]). `Default` reads as the Practices direct and lazy-loads detail when needed. `Two-Pass` first works from index entries only, lists the record IDs it needs, then opens exactly those; in Axis's benchmark it used about 38% fewer tokens on Claude with no loss of accuracy, but did not help Codex. The default Directive "Suggest a Context Method" recommends a value for the model in use; it never changes the Setting on its own.

**Range:** `Default` or `Two-Pass`

**Value:** Default

### Memo Generation

**Description:** When the Agent writes a Memo in `_Memos/` instead of putting everything in the reply (see [Practices > Memos]). Each level includes those below it. `0` = only when you ask (`^memo`). `1` = also at major milestones, such as a release or a finished phase. `2` = also for complex or multi-layered decisions, and any reply with two or more decisions for you. `3` = also for any response longer than about two screens. `4` = also for any response longer than about one screen. With a memo, the reply stays short and links to it. Missing or malformed means `2`.

**Range:** `0`, `1`, `2`, `3` or `4`

**Value:** 2

## Mindset Settings
### Reasoning

**Description:** Reasoning is computationally expensive. This setting adjusts up or down the depth of reasoning performed by the LLM.

**Range:** Relative Adjustment

**Value:** 0

### Exploration

**Description:** Exploration of different approaches/solutions is computationally expensive. Some projects do not require much exploration because a reliable approach/solution is already known; other projects require much more exploration to find the optimal solution. This setting adjusts up or down the degree of exploration (potentially in a parallel manner with Subagents) performed by the LLM (perhaps by launching parallel Subagents). Exploration is breadth of search - how many paths you try; contrast with **Creativity**, which is novelty of output. Example of the contrast: **Exploration** = 2 with **Creativity** = -2 tries many conventional variants and keeps the best; **Exploration** = -2 with **Creativity** = 2 commits to one path but produces an unconventional result.

**Range:** Relative Adjustment

**Value:** 0

### Eagerness

**Description:** The training and post-training of LLMs can cause LLMs to be "over-eager" in trying to please the User - accepting a framing because the User offered it, agreeing with User to avoid friction, and praising a request before answering or working on it. This setting adjusts up or down how far the Agent goes to accommodate and please the User. Eagerness governs the Agent's posture toward the User; contrast with **Skepticism**, which governs the Agent's posture toward its own work. Example of the contrast: **Eagerness** = -2 with **Skepticism** = -2 pushes back readily on what the User proposes while accepting its own reasoning uncritically; **Eagerness** = 2 with **Skepticism** = 2 works inside the User's framing while interrogating its own conclusions hard before delivering them.

**Range:** Relative Adjustment

**Value:** -1

### Skepticism

**Description:** Agents fail most often by believing themselves - accepting an assumption because they were the one who made it, treating a plausible reasoning path as a verified one, and reporting a conclusion whose causal explanation was never actually established. This setting adjusts up or down how hard the Agent doubts the truth and reliability of its own assumptions, claims, reasoning, evidence, and sources - asking *why* something is the case, and checking whether the explanation holds. Skepticism is doubt the Agent turns on itself while working; contrast with **Eagerness**, which governs its posture toward the User, and with **CX Frequency**, which buys independent doubt from a separate Agent after the work is done.

**Range:** Relative Adjustment

**Value:** 0

### Familiarity

**Description:** Over-familiarity between Agent and User can shape an interaction that diverts away from asking tough questions or challenging questionable results. This setting adjusts up or down the degree of familiarity in the tone of the LLM when interacting with User.

**Range:** Relative Adjustment

**Value:** 0

### Verbosity

**Description:** There is a human cost in having to wade through too much output from an LLM. This setting adjusts up or down the degree to which the LLM should narrate its actions or explain itself (irrespective of the actual degree of reasoning, exploration, etc.).

**Range:** Relative Adjustment

**Value:** 0

### Simplicity

**Description:** Every solution must balance between **Simplicity**, **Precision**, and **Generalization**. Use this setting to promote/demote **Simplicity** relative to the others.

**Range:** Relative Adjustment

**Value:** 0

### Precision

**Description:** Every solution must balance between **Simplicity**, **Precision**, and **Generalization**. Use this setting to promote/demote **Precision** relative to the others.

**Range:** Relative Adjustment

**Value:** 0

### Generalization

**Description:** Every solution must balance between **Simplicity**, **Precision**, and **Generalization**. Use this setting to promote/demote **Generalization** relative to the others.

**Range:** Relative Adjustment

**Value:** 0

### Rigor

**Description:** Rigor governs how much verification the Agent performs before accepting or delivering a result: double-checking claims against sources, re-deriving calculations, testing edge cases, and proving that requirements are actually met. More rigor produces slower, costlier, more reliable work; less rigor favors speed and accepts a higher chance of unexamined error.

**Range:** Relative Adjustment

**Value:** 1

### Creativity

**Description:** Creativity adjusts how far the Agent ranges beyond conventional, expected solutions - novel framings, lateral connections, unusual formats, and speculative options. More creativity favors originality and surprising alternatives; less creativity favors convention, predictability, and staying strictly within established patterns. Creativity is novelty of output - how unconventional the result may be; contrast with **Exploration**, which is breadth of search. Example of the contrast: **Exploration** = 2 with **Creativity** = -2 tries many conventional variants and keeps the best; **Exploration** = -2 with **Creativity** = 2 commits to one path but produces an unconventional result.

**Range:** Relative Adjustment

**Value:** 0

### Transparency

**Description:** Transparency is space inefficient. Recording every detail, of every decision, and every action, and every event would require massive amounts of storage; and auditing all of those details would require enormous amounts of computation. This setting adjusts up or down the degree to which ongoing work is recorded as it happens, and therefore the degree to which the User or Agent can return to re-construct and audit the record. Interpret relative adjustments as: 2 = audit every non-trivial decision, step, deliverable, problem, error, exception; 1 = audit most decisions, steps, deliverables, problems, errors, exceptions; 0 = audit the key decisions, steps, deliverables, problems, errors, exceptions; -1 = audit only major (end-of-chain) decisions, steps, deliverables, problems, errors, exceptions; -2 = audit only the important problems, errors, exceptions.

**Range:** Relative Adjustment

**Value:** 0

### Budget

**Description:** Budget expresses how freely the Agent may spend time, tokens, and compute on discretionary work - optional Subagents, richer models, deeper exploration, fuller records. It steers the many judgment calls that no other Setting names; where a specific Setting does name the call (e.g., **CX Frequency**, **Rigor**), that specific Setting wins and Budget does not override it. Budget also drives a few hard numeric gates - see [Rules > Budget]. Budget steers discretion; it cannot meter or guarantee actual spend, since Axis cannot portably see the User's bill or token count. Interpret relative adjustments as: 2 = Unconstrained (spend freely for the best result); 1 = Flexible (spend where it clearly helps); 0 = Standard (spend proportionate to stakes); -1 = Lean (prefer the cheaper path; spend only when it matters); -2 = Frugal (minimize spend; cheapest workable path).

**Range:** Relative Adjustment

**Value:** 0
