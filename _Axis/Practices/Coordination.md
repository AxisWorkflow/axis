# Coordination
> **Purpose:** Operate an Axis Team of Agents and bounded Jobs under one accepting Main.

External-owned proposal Teams reuse these records, budgets and workspaces with explicit `proposal_only` provenance and no Main acceptance snapshot. Their internal controls project only their own proposal lifecycle; they never become project decisions. Load [Practices > ExternalTeams] for the owner-bound route, member permissions, `owner` result recipient and Main submission. Ordinary Main controls below retain their gates.

## Records and ownership

Initialize a portable `project-id:` UUID in Project metadata once. Relocation and synchronized copies retain it; an intentional fork receives a new UUID with provenance. UUIDs and hashes identify records, not people or permission. Activate one writer/dispatcher placement explicitly; Git and cloud sync are not locks. First initialization activates only a newly minted Project UUID. An existing identity, new Main, move, copy, storage change or expiry requires explicit reactivation after verifying that the previous placement is inactive.

`Teams/{ID}.md` is an immutable founding charter; `Jobs/{ID}.md` is an immutable mandate; Messages hold accepted revisions and outcomes. `Schedules/{ID}.md` is a current definition whose immutable revisions live in Messages. All IDs use [Practices > Timestamps], including Archive checks. `Teams/{ID}/members/{slot}/` holds each member's mutable `work/` and immutable `artifacts/{revision}/`; `shared/` is Main-owned and read-only to members. A `Messages/{ID}/` support folder belongs to its same-ID Message and requires that owning detail; session dispatch retains stdout/stderr plus readable recovery receipts there. Visible `_axis-transfer-*.md` recovery claims bind Inbox transfer publication and retirement and remain with their recorded transfer evidence. Uppercase indexes are replaceable views, never authority. An ordinary empty, single-link `.gitkeep` in a family directory is a release placeholder, not a record; nonempty files, directories, symlinks and hardlinks with that name remain errors.

Python helper `coordination.py` provides validation, persistence, projection and bounded dispatch bookkeeping. Without it, Main follows [Resources > Coordination-Manual] using the same Markdown contract. Canonical details begin with a Subject of at most 80 characters and a blank line, then a readable Markdown view, a trailing JSON payload and checksum as defined below. The payload carries `schema: axis.coordination/v1`, family, id, project, subject, created and issuer plus the family's fields. Validate exact schema and record identity; unknown schema or branching accepted successors holds the subject for reconciliation. Read only addressed/charter-authorized content.

## Readable record format

`coordination-record.py` defines the shared Subject-first format. A detail has `## Content` for the communication or objective, `## Details` for the complete labelled record, then `## Machine payload` with one sorted, two-space-indented JSON object in a JSON fence. A final `checksum-sha256:` line carries the lowercase SHA-256 of all preceding text, including Subject, readable view, payload and the blank line before the checksum. The footer itself is excluded. Encoding is UTF-8; LF is canonical, CRLF is normalized for this document check only, and bare CR is refused. Separate original-byte evidence digests are never normalized.

The JSON object is the machine-parsed representation. Before consumption, regenerate the readable representation from that object and require exact agreement with the complete normalized document, including its checksum. Nested fields are sorted and displayed as labelled lists; communication text is quoted and Markdown syntax escaped so content cannot impersonate structure. Unknown shape, duplicate keys, missing/mismatched checksums or disagreement holds the affected record. Never automatically re-stamp unexplained edits. Immutable records are revised with a new linked record; legitimate Schedule changes use their accepted revision path. No checksum authenticates a sender or grants authority.

Coordination details and new Submissions are bounded to 128 KiB of complete readable/payload text, with Message content still bounded to 16 KiB. Large output belongs in linked, size/digest-checked support. A timestamp-named support folder belongs to its detail's identity; it is not a second independently identified record. Ordinary user-editable Notes and other unrelated Markdown do not acquire a blanket checksum requirement.

## Local activation

For a complete executable history audit or explicitly confined host tools, load `_Axis/Resources/Checked-Session.md`. Its replay validates canonical chains and reports coverage; it does not validate business results or grant authority.


Use `coordination.py --root PROJECT_PATH --session SID placement-status` to inspect. `activate --single-writer --previous-placement-inactive [--expires UTC_TIMESTAMP]` records an explicit serialized handoff; `deactivate` stops local canonical effects. Never assert these declarations without evidence that the other placement has stopped. A normal takeover can establish the old Main is fenced on the same physical root; a copied root cannot establish remote shutdown.

The local `Flags/coordination-placement.json` binds Project UUID, physical root, host hint, current Main/Marker, storage profile, activation generation and expiry of at most 24 hours. It is ignored by Git. Canonical acceptance, transport effects and automatic starts recheck it; a missing, stale or copied binding holds those effects while read-only inspection and ordinary work remain available. Reactivation never resets retained budgets or unknown effects. It is a local fence, not a distributed lock or remote authentication.

## Team and Job admission

A charter names owning Task, objective, outputs, validator, separate leader/member slots, scope, authority, formation, limits, stop rules and resumption. The formation label and [Practices > Collaboration] describe the chosen method; no fixed formation is mandatory. The Team Leader is a separate standard-capability General Subagent, never the project Main. It coordinates and proposes; Main accepts shared changes and final completion. Consensus does not replace validation; retain dissent and unresolved questions.

Bind authority to an immutable Log recording the actual User grant; keep the owning mutable Task as a separate reference. A digest pins those exact bytes and does not grant permission. Do not edit an authority source to make an old Job runnable. A new scope or expired mandate requires separately authorized successor work and explicit disposition of the previous attempt. A native budget extension can raise cumulative monetary/runtime ceilings under the existing scope, without rewriting the original authority or reviving an expired mandate.

A Job pins its objective, exact definition revision, authority, acceptance owner, targets/action classes/exclusions, validator, resource capacity and actual monetary/runtime agreement. For new work use the native `limits.budget` version 1 policy below. Counts of launches, rounds, retries, tokens and Messages are estimates or telemetry on this path; concurrency remains a capacity control. Check all applicable User, host-route, project, Team, Schedule and Job constraints in their own scope. Unknown paid allowance never means unlimited spending; no automatic paid API fallback.

A launch is a dispatched Agent invocation, including a newly started or resumed model call. Tool calls and local commands within that same invocation do not consume additional Agent launches. An incomplete local script is not by itself a new launch. Retain launch telemetry without turning it into an extra native budget, and preserve idempotence, effect reconciliation and any separately authorized tool/effect limits.

Existing immutable records without `limits.budget` retain legacy compatibility: the helper's default 60-minute execution deadline, 3 rounds, 12 starts, concurrency 3, reporting reserve and retry/message caps still enforce their recorded semantics. These are local compatibility settings, not a provider limit or the recommended budget for new work. Count-only examples remain legacy examples until a reviewed new mandate explicitly supplies native policy. Never silently insert policy into accepted history, enlarge finite caps to simulate unlimited use, reset cumulative accounting or call a legacy example native.

## Native money/runtime budgets

`limits.budget` selects version 1 explicitly. It binds a shared `key`, original `clock_start`, `accounting_owner`, scope, approved included/incremental routes, and monetary ceiling and/or total `runtime_seconds`. Money uses an explicit currency, integer minor units and cost basis. The total runtime includes synthesis, Main review and finalization. A worker phase target does not replace this agreement. Native founding records use the authority expiry as their execution fence; actual runtime is checked separately against the original cumulative clock. See [Resources > Coordination-Manual > Native money/runtime budgets] for the exact input and command forms.

Every dispatch supplies the approved charge basis and route plus evidence: included use reserves zero additional charge, while incremental work under a monetary ceiling needs a defensible reservation. Runtime-only work may explicitly report unpriced incremental use; it must not label unknown spend zero. Reports preserve known, reserved and uncertain liability per attempt, with stable report identity. Consuming a reservation moves its accounting category rather than charging it twice. Cancellation, failed attempts, captured results and restart do not themselves erase liability. Settling cost does not reconcile an external effect.

Use `native-budget-state` to inspect retained totals and `extend-native-budget` for a separately approved cumulative increase. Actual monetary/runtime exhaustion persists a recoverable hold and requires the needed extension; a reservation-only shortage calls for reconciliation or settlement, not an automatic claim that User's budget was spent. Ask once for a genuinely missing grant and keep independent authorized work running. A valid extension retains the original clock, prior usage, reservations, uncertain effects and artifact references. Resume paused work explicitly under current authority. A terminal or authority-expired Job stays truthful history; separately authorized successor work can retain the same accounting key and reviewed artifacts.

Team-Patterns examples and `team-plan.py` previews are planning inputs, not executable charter/charge grants. A plan's summarized budget does not synthesize `limits.budget`, provider access or reliable reservation evidence. Existing adapters do not automatically supply the native charge contract; use a qualified route that supplies it or the documented manual/core procedure. Missing capability remains visible and never silently selects paid execution.

## Capacity explanation

Use `coordination.py capacity JOB [--worker-session SID] [--slot SLOT_NAME]` as a read-only explanation. It separates recorded active, dispatch-reserved and uncertain holders from policy limits and dormant charters. `Max Concurrent Sessions` minus the reserved Main slot remains project policy; Job concurrency is local; explicit aggregate policy applies to the current Job and other occupied Jobs. An unrelated paused charter without a holder does not impose its policy on new work. Team leader reservation is Team-scoped and is consumed, not counted again, when the leader occupies it. A Team query without its proposed slot is incomplete.

Administrative close alone never frees an active or uncertain holder. Existing confirmed boundary and reconciliation controls establish release. The explanation is not a live-process census: actual host-route capacity is unverified until observed on that route, and an available recorded slot grants neither execution authority nor additional budget. Retain external host observations, live/uncertain process evidence and the scope of every actual bound when deciding admission.

## Direct collaboration

New charters carry `collaboration: {version: 1, poll_seconds: 5, max_messages_per_member: 200}`. Main may select a polling interval from 1-60 seconds and a per-member Message estimate from 1-10,000 at formation. Native budgets do not stop on this count; legacy charters enforce it as their recorded cap. Every member, including the leader, can message teammates and read their workspaces. The helper creates directories before dispatch. Job scope still bounds project inputs and proposed destinations; the charter separately grants the derived own-member workspace. Existing immutable charters without this policy retain their prior rights: create a new bounded Team and dispose of old attempts explicitly before using this feature.

Carry Team ID, Job ID, attempt, slot, Job epoch, Team epoch, current writer session, workspace, peer-read scope, polling cadence and expiry in each envelope. A finite Job can cover discussion and peer review after artifact submission or validation. Paused, terminal, expired, removed or superseded participants cannot publish new discussion or edit drafts. A late Result for Main may still be retained as evidence, without reviving authority.

Address a direct Message to a member slot, `member:{slot}`, `leader`, `team` for broadcast, or `main`. These exchanges need no relay or per-message approval. The helper binds recipients to the current sessions and Team epoch; unknown or unbound recipients refuse. Cross-Team routing uses the existing boundary procedure. Worker messages never perform Main controls. Message telemetry includes artifact announcements and observation receipts. A legacy count-cap refusal or a native monetary/runtime hold never silently drops a Message; inspect the actual semantics and retained state before recovery.

Use `coordination.py team-inbox` to read canonical records, with `after` and bounded `limit`; `history: true` includes other Team exchanges. It ignores indexes and unrelated queues, returning a cursor and whether more remain. Old recipient bindings are never redirected to replacement sessions; stale or expired addressed records are labelled. `observe-message` writes one correlated observation receipt; repeating it reuses that receipt, and receipts never ask for receipts. Retain returned publication/availability times and observation/reply records when measuring latency; creation, availability, reading and substantive response are different events. Host notifications are optional pointers to these files.

Members write their own `work/`, read all member drafts/revisions, and propose peer changes from their own directory. Draft writes and deletes check the expected current digest; a new file requires a null preimage. `artifact-publish` snapshots up to 15 files of at most 64 KiB each into a new revision and publishes a canonical announcement binding exact paths, sizes and hashes. Corrections create successor revisions; existing and partial publications cannot be overwritten. Readers verify both the file inventory and its canonical announcement; changed files, changed manifests, extra files and incomplete revisions refuse.

The optional checked Team interface in [Resources > Checked-Session] enforces those tools' scope, excludes peer edits/deletes/renames and project writes, and rejects traversal, symlinks and hardlinks. Directory layout alone is not an OS sandbox. Without exclusive host tool configuration, report only the checked tools' guarantees. Running peer code remains separately subject to the Job's action/tool scope; artifact reading never grants execution.

Before replacing any member session, fence its old Marker with retirement or a kill tombstone, dispose of its work, and accept the new binding/epoch. Preserve drafts, published revisions and authorship. Refresh affected participation bindings; neither an old process nor its stored context revives write authority. Main may initialize missing directories idempotently through `workspace-init`; this never expands an old charter.

For integration, send Main a Result attaching the exact published manifest and files, proposed destinations and their expected base digests, plus evidence and conflicts. `review-changes` checks those identities and destination scope/base and reports overlapping proposals without changing any file. Main reviews authority and content, resolves overlap explicitly, rechecks the current base immediately before applying, then uses the normal project write/Git/release procedures. Main records accepted artifact IDs, destination hashes and the resulting baseline in a Decision addressed to the Team. Consensus and a passing preflight do not themselves apply or approve a change.

Direct checked publication requires qualified atomic, non-cloud-synced storage and a live verified Main placement. Short cooperating locks serialize effects; distinct member drafts remain independently owned. On serialized or unknown storage this direct tool lane is unavailable: retain the safe manual/Main-capture fallback and disclose that it does not qualify direct collaboration. Missing notifications never disable canonical inbox polling. Check inboxes at assignment start, review checkpoints, before submitting, and while awaiting replies; bounded tool waits avoid launching models merely to poll empty inboxes.

## Included routes and selected closing

For native included execution, load [Resources > Coordination-Manual > Included execution routes]. Bind the exact request and actual included-access evidence to dispatch, keep durable intent and bounded partial output, and reconcile uncertain process effects before any retry. `team-route.py` needs a trusted Host verifier; its presence does not prove provider authentication or allowance. Existing `session-adapters.py` startup is a separate legacy operation, not a substitute native Team worker route.

When the selected method requires explicit release, load [Resources > Coordination-Manual > Selected canonical closing]. Main pins participants and the release owner before the closing exchange. Ready, release, optional acknowledgment, own result and DONE use canonical records and exact artifact revisions. A closing confirmation is not process termination, capacity release, charge settlement or substantive acceptance. Without a selected contract, retain the task's ordinary completion procedure.

## Legacy shared launch-budget compatibility

This section applies only to accepted records without native `limits.budget`. Prefer native monetary/runtime policy for new work. Do not apply this launch-count renewal to a native budget or reinterpret historical records.

A later User grant can extend a shared budget without erasing earlier launches. Main records a new immutable approval Log, then calls `coordination.py amend-budget --input {JSON}` with `budget_key`, `predecessor` (null for the first renewal), `aggregate_launches` (the new cumulative total, not additional calls), and `authority` (Log ref, exact digest and expiry). The previous budget must already exist and have a finite aggregate limit. A new grant cannot reuse earlier authority bytes.

The Log must record the actual User approval and these exact standalone bindings: `coordination-budget-key: {key}`, `coordination-budget-predecessor: {latest renewal Message ID or initial}`, `coordination-budget-previous-limit: {previous total}`, `coordination-budget-total-limit: {new total}`, and `coordination-budget-expires: {authority expiry}`. Main checks the intended grant before recording it; hashes and labels are provenance, not authentication. The accepted control Message forms an immutable predecessor chain. Conflicting branches, altered approval, missing history or stale predecessor hold the affected budget.

New Jobs use the same `budget_key`, the accepted Message ID as `budget_amendment`, that Message's exact authority, and an aggregate limit no larger than its total. Admission must bind the latest renewal. Jobs bound to the same renewal retain the minimum shared aggregate limit across that cohort; a larger later Job does not override a smaller peer bound. Every earlier dispatch remains charged, even one reconciled as not performed; active reservations remain reserved. For example, 8 previously charged starts plus 12 new approved starts means a cumulative total of 20, never a reset to zero. Existing Jobs keep their former aggregate bound, local limits and deadlines; Teams keep their own limits. Dispose of old in-flight work explicitly and admit new bounded work under the renewed grant. A renewal does not authorize uncertain-effect replay, unrelated scope, spending, host changes or external actions.

The no-helper procedure retains the same exact approval, predecessor chain, cumulative count and active reservations in readable Messages. If Main cannot establish complete history or enforce the bound, hold dispatch and report the missing capability.

## Budget holds and authorized continuation

Follow [Rules > Budget]. At a real User monetary/runtime boundary, preserve results, stop affected execution and ask for the needed extension. An unresolved reservation requires reconciliation; a local worker phase target is not an exhausted User budget. Keep the Task resumable; do not automatically fail or cancel the Team merely because a limit was reached. A worker scheduling target is not the deadline for Main acceptance. Complete administrative work already covered by the grant; a local configuration error does not revoke that authority.

For legacy records, the helper permits Main `result`, `validate`, Job `succeed` and Team `complete` after the execution deadline while original authority remains valid. Native finalization is within the cumulative monetary/runtime agreement; an exhausted actual budget holds validation/completion until extension, while safe evidence capture, charge settlement and effect reconciliation remain available. Both paths retain provenance, epoch, validation and completion checks. Neither permits new execution under expired authority or a silent extension of User's actual budget.

If the helper refuses an operation, distinguish the reason and scope. A refusal of new execution does not invalidate retained results. Main may inspect and accept verified outputs through ordinary decisions. Preserve original charter bytes, event times, provenance and totals. When a technical terminal mandate cannot continue, create a linked successor only for the remaining authorized work; do not rerun validated work or invent a new allowance. A real missing extension remains a pending User decision. Lease, integrity and uncertain-effect checks still hold their affected operations.

## Dispatch and recovery

1. Validate Main's existing lease, qualified storage, placement, authority, expiry and User control. On non-atomic storage serialize under one Main; workers return proposals for capture.
2. Reserve shared capacity before fan-out. Persist assignment and attempt intent before invoking an allowlisted typed adapter. Each worker gets [Start-Subagent]'s nonce-bound envelope plus Team/Job/slot/epoch, scope and return contract. No shell text from a record executes. Persisted dispatch is mandatory for manual and native-host launches too; a Marker or envelope alone does not reserve capacity. Before launch, compare the founding mandate, persisted attempt and final envelope scopes, including every checkpoint and evidence file. Narrower attempt scope governs; a later prompt cannot widen it.
3. Retain receipts and results, then validate before accepting. For file deliverables, capture the actual files as size/digest-checked result attachments, not only path names in prose. Main can use `capture-result` with `job`, `attempt`, `body` and `attachments` (each attachment supplies `path`, with optional expected `size` and `sha256`); the helper binds worker provenance and checks the dispatched scope. Text-only results may omit attachments. A retained result is still unaccepted until the pinned validator and Main decision succeed. Rebuild affected indexes after the final accepted transition; if rebuilding fails, report the view as stale. Apply only Main-accepted controls with the expected predecessor/epoch. A worker-authored control, divergent successor or missing acceptance holds the subject. Track failed attempts and uncertain effects; do not replay unknown external actions.
4. Pause stops future dispatch at a boundary; report active workers and unconfirmed cancellation. Stop requests safe checkpoints. An observed stopped process does not itself clear retained capacity: record the truthful terminal or reconciliation transition and confirmed boundary, then recheck capacity before another dispatch. Late results cannot reopen terminal Jobs. A changed mandate gets an explicit revision and disposition of in-flight work.
5. Replace a leader only through an accepted membership/binding event and a new epoch/session. Recover from charter, assignments, retained results and checkpoint, not private conversation. No automatic replacement unless explicitly authorized. On actual monetary/runtime exhaustion preserve partial work and request the needed extension under [Rules > Budget]; reconcile reserved/uncertain liability separately. For a legacy count/deadline refusal, retain the record and explicitly select an authorized continuation rather than interpreting a local count as a new User budget.

Team states: draft, ready, running, paused, completed, failed, cancelled. Job states: proposed, admitted, running, blocked, pause-requested, paused, succeeded, failed, cancelled, expired. Only validated outputs and Main acceptance justify success.

## Retained locks and uncertain effects

A retained coordination, scheduler or transfer lock holds the affected writes; it does not establish whether its Job completed. Keep the lock, causal records, transfer receipts and exact output bytes. No age threshold, stale Marker or stopped process alone permits reclaiming it.

Use [Resources > Lock-File > Quiescent Recovery] only when User or trusted host controls have stopped all possible writers and suspended new sessions, timers and spawns for the entire recovery. Record that exclusion and the selected lock's identity, OWNER bytes and directory contents before removal. Unexpected contents, changed ownership, partial records or an unverified remote writer keep the affected operation held. Remove only the verified abandoned lock, preserving its evidence and every target; then reacquire normally.

After recovery, inspect immutable intent/results and output digests before projecting the Job and rebuilding indexes. Reconcile an effect only from sufficient evidence: a verified accepted output is retained, proven non-performance may permit an authorized retry, and an unknown outcome remains blocked. Lock removal never grants a retry, clears budget or proves success. Report safe hold, manual recovery and successful work separately; never claim generic automatic recovery.

## Session and transfer boundaries

Distinguish desired residency (on-demand/warm/managed), observed runtime and Axis lease authority. On-demand is default. Warm context does not renew a lease; managed restart and reboot restoration need explicit opt-in. Bind Project UUID/root, Axis Session ID, exact host handle/generation, adapter/version and verified operations. Never use PID, pane title or most-recent conversation alone.

Use `session-adapters.py` or the optional `axis` launcher only for verified typed capabilities. Unsupported or uncertain operations return their limitation; retain the manual separate-session path. No process may synthesize a Main heartbeat. If no separate session exists, report the dedicated-team capability unavailable.

Inbox transfers persist prepared, copied-and-verified, destination-accepted and source-retired receipts. Keep the source until exact receiver acceptance; only its owning Main retires unchanged bytes. Hold symlinks, collisions, partial arrivals and changed bytes. Routing authority comes from User's rule, never the document. See [Practices > Messages] and [Practices > Scheduling].

History lookup reads direct timestamped records in the relevant Archive family folder and compatible flat four-digit year folders; it does not recurse through unrelated evidence or Message support folders. Relevant cloud-only macOS records are reported as unavailable before opening them; make those specific records local before retrying. A filesystem call can still block on an unresponsive mount. Index rebuild requires an accessible Archive root and leaves prior indexes unchanged if the history scan fails.

An unavailable configured Archive makes historical deduplication and budget accounting unverified. Hold new Job admission, dispatch and automatic session/transfer starts until required history is available; never interpret a missing archive as an empty history. Local pause/stop and ordinary unrelated project work remain available.

Compact indexes show at most 100 rows within a 60,000-byte table budget, with exact total and pending counts and an explicit truncation notice. Messages shows Main-recipient pending obligations first, then uncertain classifications, other peer pending/history and newest resolved records. The global pending count remains history telemetry; `main-pending-count` and `main-uncertain-count` are separate cached hints for canonical review, as described in [Practices > Messages]. Complete immutable details remain in the family folder and configured Archive; a bounded view never discards records or changes pending state.

## Evidence for interruption and completion

For a controlled interruption test, distinguish file visibility from a completed checkpoint. If the observer needs a readiness receipt, include its path in the mandate, persisted dispatch and envelope before launch. Emit it only after the required output flush, close and exact readback; bind those bytes by size and digest. The observer verifies the receipt before interrupting its owned process. A missing receipt proves neither completion nor absence of an effect.

On recovery, distinguish the last durable checkpoint, the host command actually issued and the controller's termination observation. A planned wait or a zero exit status does not prove that a wait ran or that work completed. Inspect canonical records and exact output bytes before reusing a result; label missing evidence unknown. Treat a wait duration as a maximum observation interval unless the mandate explicitly requires elapsed-time testing, and stop waiting when the required result is already validated. Never use an invented or approximate completion timestamp: obtain current UTC when recording completion, while separately preserving any evidenced event time. Scratch work belongs under the project's `_Temp/`; a host environment variable naming another scratch directory does not enlarge the assigned write scope. Before launching a separate session, bind the host’s supported temporary-directory variables for that invocation to a checked directory under the target project’s `_Temp/`, and verify its effective scratch path. Do not change persistent host settings. A temporary-directory binding is a location preference, not a filesystem sandbox; retain scope checks and stop on an observed escape.

Validation covers prose claims as well as totals: a correct calculation does not validate an unsupported count or a strict ordering where values tie. Report only the precision and comparisons the retained source establishes. A finite Schedule test proves only its observed evaluations and admitted Jobs; it does not establish permanent admission or future execution.

## Collaboration plans

For Team setup load [Practices > Teams] and [Practices > Collaboration]. Infrastructure does not impose one working method. The optional embedded `collaboration_plan` is checked against the charter roles/concurrency and pinned by canonical SHA-256. The coordinator loads `team-plan.py` only when this field is present. Legacy prose charters remain manual/unclassified. Preview consistency and derived review obligations do not grant authority or certify substantive work. Formal method amendments carry the replacement plan and in-flight disposition through the existing accepted epoch transition; they cannot enlarge scope or limits. An amendment advances Team epoch: old participation bindings do not silently migrate. Preserve accepted checkpoints and explicitly reconcile or replace affected attempts before resuming discussion under current bindings; late results remain evidence rather than renewed execution authority. The original budget summary in the plan identifies its founding grant, while accepted budget extensions supply current effective ceilings.
