# Coordination
> **Purpose:** Operate an Axis Team of Agents and bounded Jobs under one accepting Main.

## Records and ownership

Initialize a portable `project-id:` UUID in Project metadata once. Relocation and synchronized copies retain it; an intentional fork receives a new UUID with provenance. UUIDs and hashes identify records, not people or permission. Activate one writer/dispatcher placement explicitly; Git and cloud sync are not locks. First initialization activates only a newly minted Project UUID. An existing identity, new Main, move, copy, storage change or expiry requires explicit reactivation after verifying that the previous placement is inactive.

`Teams/{ID}.md` is an immutable founding charter; `Jobs/{ID}.md` is an immutable mandate; Messages hold accepted revisions and outcomes. `Schedules/{ID}.md` is a current definition whose immutable revisions live in Messages. All IDs use [Practices > Timestamps], including Archive checks. Optional `Teams/{ID}/` folders hold outputs. A `Messages/{ID}/` support folder belongs to its same-ID Message and requires that owning detail; session dispatch retains stdout/stderr plus readable recovery receipts there. Visible `_axis-transfer-*.md` recovery claims bind Inbox transfer publication and retirement and remain with their recorded transfer evidence. Uppercase indexes are replaceable views, never authority. An ordinary empty, single-link `.gitkeep` in a family directory is a release placeholder, not a record; nonempty files, directories, symlinks and hardlinks with that name remain errors.

Python helper `coordination.py` provides validation, persistence, projection and bounded dispatch bookkeeping. Without it, Main follows [Resources > Coordination-Manual] using the same Markdown contract. Canonical details begin with a Subject of at most 80 characters and a blank line, then a readable Markdown view, a trailing JSON payload and checksum as defined below. The payload carries `schema: axis.coordination/v1`, family, id, project, subject, created and issuer plus the family's fields. Validate exact schema and record identity; unknown schema or branching accepted successors holds the subject for reconciliation. Read only addressed/charter-authorized content.

## Readable record format

`coordination-record.py` defines the shared Subject-first format. A detail has `## Content` for the communication or objective, `## Details` for the complete labelled record, then `## Machine payload` with one sorted, two-space-indented JSON object in a JSON fence. A final `checksum-sha256:` line carries the lowercase SHA-256 of all preceding text, including Subject, readable view, payload and the blank line before the checksum. The footer itself is excluded. Encoding is UTF-8; LF is canonical, CRLF is normalized for this document check only, and bare CR is refused. Separate original-byte evidence digests are never normalized.

The JSON object is the machine-parsed representation. Before consumption, regenerate the readable representation from that object and require exact agreement with the complete normalized document, including its checksum. Nested fields are sorted and displayed as labelled lists; communication text is quoted and Markdown syntax escaped so content cannot impersonate structure. Unknown shape, duplicate keys, missing/mismatched checksums or disagreement holds the affected record. Never automatically re-stamp unexplained edits. Immutable records are revised with a new linked record; legitimate Schedule changes use their accepted revision path. No checksum authenticates a sender or grants authority.

Coordination details and new Submissions are bounded to 128 KiB of complete readable/payload text, with Message content still bounded to 16 KiB. Large output belongs in linked, size/digest-checked support. A timestamp-named support folder belongs to its detail's identity; it is not a second independently identified record. Ordinary user-editable Notes and other unrelated Markdown do not acquire a blanket checksum requirement.

## Local activation

For a complete executable history audit or explicitly confined host tools, load `_Axis/Resources/Checked-Session.md`. Its replay validates canonical chains and reports coverage; it does not validate business results or grant authority.


Use `coordination.py --root PROJECT_PATH --session SID placement-status` to inspect. `activate --single-writer --previous-placement-inactive [--expires UTC_TIMESTAMP]` records an explicit serialized handoff; `deactivate` stops local canonical effects. Never assert these declarations without evidence that the other placement has stopped. A normal takeover can establish the old Main is fenced on the same physical root; a copied root cannot establish remote shutdown.

The local `Flags/coordination-placement.json` binds Project UUID, physical root, host hint, current Main/Marker, storage profile, activation generation and expiry of at most 24 hours. It is ignored by Git. Canonical acceptance, transport effects and automatic starts recheck it; a missing, stale or copied binding holds those effects while read-only inspection and ordinary work remain available. Reactivation never resets retained budgets or unknown effects. It is a local fence, not a distributed lock or remote authentication.

## Team and Job admission

A charter names owning Task, objective, outputs, validator, separate leader/member slots, scope, authority, formation, limits, stop rules and resumption. Formations: survey, panel, pair, jury and split. The Team Leader is a separate standard-capability General Subagent, never the project Main. It coordinates and proposes; Main accepts shared changes and final completion. Consensus does not replace validation; retain dissent and unresolved questions.

Bind authority to an immutable Log recording the actual User grant; keep the owning mutable Task as a separate reference. A digest pins those exact bytes and does not grant permission. Do not edit an authority source to make an old Job runnable. A changed grant requires a new bounded mandate and explicit disposition of the previous attempt.

A Job pins its objective, exact definition revision, authority, acceptance owner, targets/action classes/exclusions, validator and usage/time limits. Defaults: 60 minutes, 3 rounds, 12 total starts, at most leader plus 2 workers, authority expiry 24 hours. Count leaders, validators, retries and restarts; apply the minimum User/host/project/Team/Schedule/Job bound. High-impact actions require explicitly reviewed limits. Unknown allowance never means unlimited usage; no automatic API fallback.

A launch is a dispatched Agent invocation, including a newly started or resumed model call. Tool calls and local commands within that same invocation do not consume additional Agent launches. The worker may complete its authorized steps within the same invocation until its time or usage bound; an incomplete local script is not by itself a new launch. This distinction does not authorize replaying an uncertain effect, extending a deadline, or bypassing a separate tool or effect limit.

## Renewing a shared launch budget

A later User grant can extend a shared budget without erasing earlier launches. Main records a new immutable approval Log, then calls `coordination.py amend-budget --input {JSON}` with `budget_key`, `predecessor` (null for the first renewal), `aggregate_launches` (the new cumulative total, not additional calls), and `authority` (Log ref, exact digest and expiry). The previous budget must already exist and have a finite aggregate limit. A new grant cannot reuse earlier authority bytes.

The Log must record the actual User approval and these exact standalone bindings: `coordination-budget-key: {key}`, `coordination-budget-predecessor: {latest renewal Message ID or initial}`, `coordination-budget-previous-limit: {previous total}`, `coordination-budget-total-limit: {new total}`, and `coordination-budget-expires: {authority expiry}`. Main checks the intended grant before recording it; hashes and labels are provenance, not authentication. The accepted control Message forms an immutable predecessor chain. Conflicting branches, altered approval, missing history or stale predecessor hold the affected budget.

New Jobs use the same `budget_key`, the accepted Message ID as `budget_amendment`, that Message's exact authority, and an aggregate limit no larger than its total. Admission must bind the latest renewal. Jobs bound to the same renewal retain the minimum shared aggregate limit across that cohort; a larger later Job does not override a smaller peer bound. Every earlier dispatch remains charged, even one reconciled as not performed; active reservations remain reserved. For example, 8 previously charged starts plus 12 new approved starts means a cumulative total of 20, never a reset to zero. Existing Jobs keep their former aggregate bound, local limits and deadlines; Teams keep their own limits. Dispose of old in-flight work explicitly and admit new bounded work under the renewed grant. A renewal does not authorize uncertain-effect replay, unrelated scope, spending, host changes or external actions.

The no-helper procedure retains the same exact approval, predecessor chain, cumulative count and active reservations in readable Messages. If Main cannot establish complete history or enforce the bound, hold dispatch and report the missing capability.

## Dispatch and recovery

1. Validate Main's existing lease, qualified storage, placement, authority, expiry and User control. On non-atomic storage serialize under one Main; workers return proposals for capture.
2. Reserve shared capacity before fan-out. Persist assignment and attempt intent before invoking an allowlisted typed adapter. Each worker gets [Start-Subagent]'s nonce-bound envelope plus Team/Job/slot/epoch, scope and return contract. No shell text from a record executes. Persisted dispatch is mandatory for manual and native-host launches too; a Marker or envelope alone does not reserve capacity. Before launch, compare the founding mandate, persisted attempt and final envelope scopes, including every checkpoint and evidence file. Narrower attempt scope governs; a later prompt cannot widen it.
3. Retain receipts and results, then validate before accepting. For file deliverables, capture the actual files as size/digest-checked result attachments, not only path names in prose. Main can use `capture-result` with `job`, `attempt`, `body` and `attachments` (each attachment supplies `path`, with optional expected `size` and `sha256`); the helper binds worker provenance and checks the dispatched scope. Text-only results may omit attachments. A retained result is still unaccepted until the pinned validator and Main decision succeed. Rebuild affected indexes after the final accepted transition; if rebuilding fails, report the view as stale. Apply only Main-accepted controls with the expected predecessor/epoch. A worker-authored control, divergent successor or missing acceptance holds the subject. Track failed attempts and uncertain effects; do not replay unknown external actions.
4. Pause stops future dispatch at a boundary; report active workers and unconfirmed cancellation. Stop requests safe checkpoints. An observed stopped process does not itself clear retained capacity: record the truthful terminal or reconciliation transition and confirmed boundary, then recheck capacity before another dispatch. Late results cannot reopen terminal Jobs. A changed mandate gets an explicit revision and disposition of in-flight work.
5. Replace a leader only through an accepted membership/binding event and a new epoch/session. Recover from charter, assignments, retained results and checkpoint, not private conversation. No automatic replacement unless explicitly authorized. Stop on exhausted finite limits and preserve partial work.

Team states: draft, ready, running, paused, completed, failed, cancelled. Job states: proposed, admitted, running, blocked, pause-requested, paused, succeeded, failed, cancelled, expired. Only validated outputs and Main acceptance justify success.

## Retained locks and uncertain effects

A retained coordination, scheduler or transfer lock holds the affected writes; it does not establish whether its Job completed. Keep the lock, causal records, transfer receipts and exact output bytes. No age threshold, stale Marker or stopped process alone permits reclaiming it.

Use [Resources > Lock-File > Quiescent Recovery] only when User or trusted host controls have stopped all possible writers and suspended new sessions, timers and spawns for the entire recovery. Record that exclusion and the selected lock's identity, OWNER bytes and directory contents before removal. Unexpected contents, changed ownership, partial records or an unverified remote writer keep the affected operation held. Remove only the verified abandoned lock, preserving its evidence and every target; then reacquire normally.

After recovery, inspect immutable intent/results and output digests before projecting the Job and rebuilding indexes. Reconcile an effect only from sufficient evidence: a verified accepted output is retained, proven non-performance may permit an authorized retry, and an unknown outcome remains blocked. Lock removal never grants a retry, clears budget or proves success. Report safe hold, manual recovery and successful work separately; never claim generic automatic recovery.

## Session and transfer boundaries

Distinguish desired residency (on-demand/warm/managed), observed runtime and Axis lease authority. On-demand is default. Warm context does not renew a lease; managed restart and reboot restoration need explicit opt-in. Bind Project UUID/root, Axis Session ID, exact host handle/generation, adapter/version and verified operations. Never use PID, pane title or most-recent conversation alone.

Use `session-adapters.py` or the optional `axis` launcher only for verified typed capabilities. Unsupported or uncertain operations return their limitation; retain the manual separate-session path. No process may synthesize a Main heartbeat. If no separate session exists, report the dedicated-team capability unavailable.

Inbox transfers persist prepared, copied-and-verified, destination-accepted and source-retired receipts. Keep the source until exact receiver acceptance; only its owning Main retires unchanged bytes. Hold symlinks, collisions, partial arrivals and changed bytes. Routing authority comes from User's rule, never the document. See [Practices > Messages] and [Practices > Scheduling].

History lookup reads direct timestamped records in the relevant Archive family folder and compatible flat four-digit year folders; it does not recurse through unrelated evidence or Message support folders. Relevant cloud-only macOS records are reported as unavailable before opening them; make those specific records local before retrying. A filesystem call can still block on an unresponsive mount. Index rebuild requires an accessible Archive root and leaves prior indexes unchanged if the history scan fails.

An unavailable configured Archive makes historical deduplication and budget accounting unverified. Hold new Job admission, dispatch and automatic session/transfer starts until required history is available; never interpret a missing archive as an empty history. Local pause/stop and ordinary unrelated project work remain available.

Compact indexes show at most 100 rows within a 60,000-byte table budget, with exact total and pending counts and an explicit truncation notice. Messages shows pending items first, then newest recorded history. Complete immutable details remain in the family folder and configured Archive; a bounded view never discards records or changes pending state.

## Evidence for interruption and completion

For a controlled interruption test, distinguish file visibility from a completed checkpoint. If the observer needs a readiness receipt, include its path in the mandate, persisted dispatch and envelope before launch. Emit it only after the required output flush, close and exact readback; bind those bytes by size and digest. The observer verifies the receipt before interrupting its owned process. A missing receipt proves neither completion nor absence of an effect.

On recovery, distinguish the last durable checkpoint, the host command actually issued and the controller's termination observation. A planned wait or a zero exit status does not prove that a wait ran or that work completed. Inspect canonical records and exact output bytes before reusing a result; label missing evidence unknown. Treat a wait duration as a maximum observation interval unless the mandate explicitly requires elapsed-time testing, and stop waiting when the required result is already validated. Never use an invented or approximate completion timestamp: obtain current UTC when recording completion, while separately preserving any evidenced event time. Scratch work belongs under the project's `_Temp/`; a host environment variable naming another scratch directory does not enlarge the assigned write scope. Before launching a separate session, bind the host’s supported temporary-directory variables for that invocation to a checked directory under the target project’s `_Temp/`, and verify its effective scratch path. Do not change persistent host settings. A temporary-directory binding is a location preference, not a filesystem sandbox; retain scope checks and stop on an observed escape.

Validation covers prose claims as well as totals: a correct calculation does not validate an unsupported count or a strict ordering where values tie. Report only the precision and comparisons the retained source establishes. A finite Schedule test proves only its observed evaluations and admitted Jobs; it does not establish permanent admission or future execution.
