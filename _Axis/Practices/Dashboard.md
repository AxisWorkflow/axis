# Dashboard
> **Purpose:** Define the Dashboard web app that gives User a live overview.

The Dashboard is the live view of a project; a Status Report is the static one (see [Practices > Status]). The Dashboard reads the project's files continuously and refreshes itself every 30 seconds - it has no snapshot mode, no offline mode, and no way to stop it refreshing, because a Dashboard that is not live is just a worse Status Report. It therefore requires a running web server, and when User cannot run one the answer is `^status`, not a degraded Dashboard. Keep that split: never add a static or exported mode to the Dashboard, and never derive a shareable artifact from it.

Axis ships with a default dashboard as a web application built in HTML/Javascript (`_Axis/Dashboard/index.html`) and a read-only server (`_Axis/Dashboard/server.py`). Launch it with `^dashboard`. The server binds only to loopback and exposes only the specific files, filtered listings, `Last-Modified` metadata, and pinned same-origin Mermaid asset the Dashboard consumes. It denies `_Axis/Secrets/`, `_Temp/`, `.git/`, host configuration, symlinks, traversal, and write methods; sensitive Flags such as `environment-binding`, `reminder-check`, `session-id`, and `starting` remain outside its allowlist. For Subprojects it performs no Subproject discovery (recognition is child-initiated and parent-side discovery is on-demand - see [Practices > Subprojects]) and serves no child content beyond the parent's own allowlist. It also serves nothing named `Secrets` at any depth, and the read contract covers only the parent's declared identity files; it never exposes child content or discovers arbitrary descendants. Never serve the project root with a general-purpose static server. The initial dashboard is very basic. Revise and extend the dashboard by working with User to fit their needs and the needs of the project; update the server allowlist and its security tests whenever a new card needs a new path.

When operational findings exist, the default Dashboard opens with a short full-width untitled findings card; when none exist, omit the card and reserve no gap. Three vertical cards follow in coordinated faded colors: Configuration, a deliberately compact Mindset card, and Agents. The first thin rule comes after that opening row. Project then runs tall down the left column while Ideas, Notes, Logs, Reminders, User Follow Up, and Agent Activity stack in that exact order down the right. When Wiki is in use its conditional full-width card follows that section. A second rule begins the full-width Plan card; full-width Tasks and Status Report cards follow Plan directly, separated only by the ordinary grid gap. All horizontal rules are one-pixel lines with moderate contrast in light and dark modes. The Project/activity pair collapses to one column on narrow screens. Initial sections include:

Dashboard emphasis stays controlled rather than heavy: every direct card title uses the stronger weight 650, other headings use 600, and authored bold content plus most detail values use the lighter weight 500. Important Status notices remain 550. The exact routine values `Standard`, `✓`, and `-` render at normal weight 400 so ordinary healthy state does not compete for attention.

- **Header** - a dark full-width band: the title plus Project Name in a larger bold face (omitted until the project is set), with the compact Metrics line at the top right. Every metric puts its count before its label. Metrics remain ordered Agents, Tasks, Ideas, Notes, Logs, Status Reports, Snapshots, CX, Audit; overdue Snapshot and Status Report counts tint amber at their documented cadences.
- **Configuration** - the first card in the opening row: one uninterrupted aligned label/value list with Title Case labels and the retired Host summary omitted. Its exact order is Version, Profile, Main Model, Local Model, CX Model, CX Frequency, Last Snapshot, Portability, Spawn, Parallel, Shell, Cloud-Safe, Local Endpoint, Local Subagents, Local Platform. `Max Notes` is not displayed here; it remains a Status-notice threshold. Downgrades also stay out of Configuration and appear in Status. `same-as-host` resolves to the actual model. Valid `yes` capabilities display `✓`; `no` displays `Unavailable`; missing, malformed, blank, and `cleared` Flags display `Unknown`. Cloud-Safe requires both `Storage Policy=auto` and `host-storage=atomic`; `single-writer` or `serialized` displays `Unavailable`, while missing/malformed policy or `unknown` storage displays `Unknown`. Last Snapshot age comes from its canonical UTC filename, not clone/copy-sensitive filesystem `mtime`. Portability reads `Ready`, `Degraded`, or `Unverified` from the newest Snapshot Continuity block. Local Platform is the selected local model's per-machine Axis readiness state. It reads `N/A` when no supported local endpoint is reachable this session; it reads `Unknown` when an endpoint may be usable but the selected model or matching aptitude scorecard cannot be validated. Otherwise it reads `Ready`, `Retest`, or `Review`.
- **Mindset** - the compact second card in the opening row: every Mindset Setting is one compact row, with the name in the left column and its substantive adjustment plus signed source value aligned nearby in the right. Values read `Much Less -2`, `Less -1`, `-`, `More +1`, or `Much More +2`; zero uses the lone dash instead of `Default`. Missing, malformed, decimal, and out-of-range values read `Unknown`.
- **Agents** - the third opening card. It lists Markers from `_Axis/Agents/` (role, start time, run time; a Marker with a `.kill` tombstone beside it shows as stopped, and stale Markers are flagged).
- **Reminders** - the portable Reminder queue, ordered malformed, overdue/due, then upcoming by exact UTC. It retains the validated schema, target-safe links, explicit due state, and the empty state `No open Reminders.`; it never implies that browser refresh is a background notification service.
- **User Follow Up** - the complete live User-owned Follow-Up queue, ordered overdue/earliest due first and then undated oldest. It retains count, due state, Subject, self-contained ask, record links, malformed-review visibility, and the empty state `No open Follow-Ups.`
- **Agent Activity** - due work or maintenance the Agent can advance, ranked by how overdue each item is. This is prospective Agent-owned work, not a history of completed activity. It uses the oldest Active Task's durable `updated:` time at 7+ days, an `Unknown` Task recency, a Snapshot older than 48 hours, no Status Report in the last 7 days, and Ideas whose `reviewed:` field is empty; it never uses Task-detail `mtime`, and cadence rows stay quiet until the first Log. Its healthy empty state is `Nothing is overdue.`
- **Untitled findings card** - a short, conditional, full-width card above the opening row. It deliberately has no heading because every bullet must stand on its own. Deterministic browser rules inspect the load-bearing evidence from project setup, stale Markers or locks, queued requests, the Notes limit, unavailable or unconfirmed Host facts, every matching `Capability downgrade:` record in the bounded recent-Log scan, and the newest Snapshot's privacy-safe Continuity infrastructure summary, then list only the resulting conditions. Infrastructure notices name only declared logical items whose saved status is `absent` or `unverified`; `present` and `not-applicable` items stay invisible, and the browser never reads Environment or Secrets content to produce them. A malformed infrastructure summary becomes one generic verification notice without echoing its contents. This is broader than a raw exception list but is not Agent reasoning and is shallower than `^status`: do not analyze commits, project outcomes, deliverable coverage, or long-term trends here; those belong in a full Status Report. Do not add an aggregate issue-count sentence above the entries. Each entry stands alone: name the affected capability or feature, state what is unavailable or unknown and why when known, then state the practical consequence, fallback, or User impact. For example: `Local Subagents are unavailable in this session because no local model endpoint was detected.` A card or header region that cannot finish reading keeps its own local fallback but does not add refresh mechanics here; the footer identifies the whole refresh as partial instead. Particularly important notices use faded red and weight 550; project setup is one such notice and reads `⚠ Project setup incomplete - ask your Agent for help.` Never emit a label fragment, a context-dependent pointer such as `see above`, or a bare machine field. When no operational conditions exist, omit the entire card and reserve no space.
- **Ideas, Notes, Logs, Tasks, and Status Report** - the record family, tinted in complementary colors and capped at a shared height with internal scrolling. Ideas, Notes, and Logs form the first three cards in the right-hand stack beside Project. The full-width Tasks card follows Plan with no intervening rule and shows per-Status counts and age labels. The full-width Status Report card follows Tasks with no intervening rule. It shows the newest saved report distilled to its opening synopsis paragraph, or exact empty state `No Status Report yet - use ^status.` when none exists. Logs opens with a 14-day sparkline of events per day, derived from timestamp filenames alone. The Dashboard has no separate Recent Developments card: the richer `## Recent Developments` analysis, including commits, belongs in the Status Report produced by `^status`.
- **Wiki** - a full-width card below the record family: page count, latest activity, and the newest open questions from the Library Status record (shown only when the Wiki is in use).
- **Project and Plan** - Project is the white tall left column beside the six-card activity stack (every section of `_Axis/PROJECT.md` rendered read-only, each bold heading followed inline by a short plain-font parenthetical gloss, placeholders shown as TBD). Plan is a separately tinted full-width card below the working section (summary, stage chips, and the `^plan` diagram rendered with the pinned same-origin Mermaid bundle when possible; the underlying diagram link remains when rendering fails).
- **Footer** - a fixed bar pinned to the bottom of the viewport (always visible, no scrolling needed), in a lighter dark grey than the header: the locale-formatted refresh timestamp alone on the far left after a complete refresh, and a light Reload button on the far right. When any card or header region cannot finish reading, prefix the timestamp with exact `Partial Refresh on: `; keep the affected region's local fallback, and remove the prefix on the next complete refresh. Never use a generic `Refreshed` prefix. The button forces the browser to re-read the approved Workflow files and recompute its deterministic views while the page continues its automatic 30-second cycle; it never invokes an Agent or model. Agent judgment appears only after an Agent writes a source record that the next refresh can read. A manual Reload immediately shows a visible busy state, reports completion, and exposes both states to assistive technology so the click never appears inert.
