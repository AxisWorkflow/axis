# Markers
> **Purpose:** Define ephemeral Markers that track in-flight activity.

A Marker is a short-term, ephemeral tracking file. A Marker indicates that something is in flight *right now* - it records status, not history.

- Markers live in `_Axis/Agents/` - one per live Subagent (see [Start-Subagent > How to Track Subagents]) and one per live Main Agent session (written at Session Start).
- Subjects distinguish the types: `Subagent: {role}` for Subagents; `Main: session` for a Main session; `External: {host}` for an External Agent session (refreshed on every served request; deleted by `^shutdown`).
- Name each Marker `{yyyy.mm.dd.hh.mm.ss.xxxZ}.md` and follow the Index-Detail Pattern (Line 1 is the Subject). A Main Marker is named with its session's Session ID and carries `session: {Session ID}` in its body - a foreign `Main: session` Marker is one whose session line differs from yours.
- Write a Marker when the tracked activity starts; delete a Subagent Marker when the Subagent returns.
- An abrupt or ordinary host close has no reliable end hook, so a Main Marker left behind ages out at 1 hour. An explicit successful `^shutdown`, or a verified `^update` whose literal `UPDATE` confirmation includes the mandatory restart, is a reliable exit and deletes the actor's own Marker. Main Markers are refreshed (`mtime` touch) by `^save`, on session resume, and on every Log write (see [Practices > Logs]). A fresh foreign `Main: session` Marker at startup means another session may be active: coordinate shared writes via [Lock-File].
- A Marker older than 1 hour (`mtime` > 3600s) is presumed dead and obsolete; delete it during any cleanup pass (warn User, but do not hard-block).
- A Marker whose `{ID}.kill` tombstone sits beside it is DEAD at any age, however fresh its `mtime` looks. Every scan that asks "is this agent live?" - Session Start's boot scan, the entry file's role recognition and fast-path glance, `^kill`'s listing, `^refresh`'s sweep, the Dashboard's Agents card - must check for the sibling before answering yes. This is not cosmetic: on a surface that cannot delete, the kill leaves the Marker in place ([Rules > HostAndMeta > Deletion Fallback]), so a killed agent reads as live for a full hour. For an External target that is a reporting error; for a Main target it strands the project, because the next boot degrades to External beside a corpse.
- A fresh `Subagent:` Marker with no fresh `Main: session` Marker behind it is an orphan - evidence of a crashed spawn, not live work. Report it during Session Start; it ages out like any other Marker and `^refresh` clears it once stale.
- Markers are ephemeral session-state, never WORM, and excluded from version control.
- Never archive a Marker. If deletion is blocked, clear it or move it to `_Trash/` under [Rules > HostAndMeta > Deletion Fallback].
- Do NOT use a Marker for state that must survive the session - use a Flag instead.

## The Lease

Your Marker is your lease on acting. Re-verify it at the start of every turn and immediately before every shared write or lock take - by READING it, never by a bare `touch`, because a `touch` on a missing path creates the file and a verification that manufactures its own subject can never fail. Serving a turn also RENEWS the lease: once the turn-start read passes, refresh your Marker (an `mtime` touch) - renewal always follows a successful read and NEVER creates a Marker. "Follows" is literal: the touch is a SEPARATE action taken after you have judged what the read returned, never chained into the same command, because a chained touch executes before you have seen the result. A live but quiet agent then never reads as stale, and staleness (over 1 hour) measures exactly one thing: an agent that stopped serving turns. This is not background doctrine - it has executable homes, one per kind of write: the entry file's fast path performs the read-then-touch on every served turn; [Lock-File > Acquire] performs the pre-write check before any lock; and [Practices > Timestamps] step 3 performs it before the atomic claim, which is the only path EVERY new record takes. That third home exists because append-only records - Logs, Notes, Ideas, Status, CX, Tracking - are new files that take no lock, so a check anchored only to locking never fires for them. The fast path recognizes a BOOT RECORD, not a banner - a Main's Session ID banner or an External's minted Session ID and `External:` Marker - because the entry file is the only instruction either role re-reads per turn, and a renewal rule that fires for one role only leaves the other ageing out while it is still serving. Then:

- A tombstone `_Axis/Agents/{your ID}.kill` present means you are KILLED: Log one final Event, append a final Tracking line, tell User on your own surface, and stop serving permanently - any later message in the conversation gets one line, and you never write anything else.
- Your Marker missing WITHOUT a tombstone is NOT a kill - a sweep or sync hiccup can do that. Stop writing and ask User, in that turn's answer; do NOT re-create the Marker yourself to carry on, because re-registering silently is indistinguishable from never having noticed. Re-register it once on User's word; on a second disappearance in the same session, stop for good.
- Tombstones are written only by `^kill` (User-only, sender-verified); `^shutdown` is the graceful self-exit that deletes your own Marker so the next boot finds a quiet project. A stale tombstone (`mtime` > 1 hour) is cleanup: `^refresh` deletes it silently.
